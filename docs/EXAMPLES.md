# Worked examples

[繁體中文](EXAMPLES.zh-TW.md) · [README](../README.md)

These are fictional application scenarios. The linked Markdown documents were generated by the actual CLI in temporary Git repositories. Completion and verification notes simulate a developer's report; the CLI did not implement or test an API.

Assume both collaborators installed Sidepact, ran `sidepact enable` in their actual application repositories, and reloaded their agent instructions. No init or recipient setup is required. Commands below illustrate what the agent runs; engineers can also run them directly.

## 1. Frontend needs an avatar field: a complete round trip

**User asks the frontend agent:**

> Add an avatar to the member page, with a default image when no avatar exists.

**Agent checks the task and known contract:**

```ts
// contracts/profile.ts:1 — existing contract in this scenario
export type ProfileResponse = { name: string };

// src/profile.ts:3 — frontend display requirement
export type DisplayProfile = { name: string; avatarUrl: string | null };
```

Outcome: **cross-repo work required** to extend the known interface. The receiving team still needs to check the actual backend; absence from this contract is not proof that the server has no equivalent field.

The agent supplies behavior, file/line evidence, proposed fields, acceptance criteria, and questions:

```bash
# Inside the frontend repo, with uncommitted tracked changes
sidepact generate --note "[required] Extend GET /api/me avatar contract; evidence: member page requires avatarUrl but the known contract has only name; propose string or null; verify both avatar/no-avatar cases; backend must check its implementation"
```

The agent reports the original handoff ID and `handoffs/<id>/改動.md` path. The user sends that local file through Telegram; there is no separate download or automatic delivery.

Read the [complete generated handoff](../examples/avatar/改動.md) (Traditional Chinese example). Its body contains the changed file, numbered task, evidence, and proposed acceptance criteria. Send the **whole file**, including front matter, rather than copying only the visible checklist.

**Backend operator gives the file to their agent:**

> Import this Sidepact handoff, check it against the actual API, implement agreed work, and generate a reply. Ask about unresolved assumptions.

Inside the backend repo:

```bash
sidepact import /path/to/received/改動.md
sidepact show <original-id>

# Only after implementation and appropriate verification; replace the note with actual results
sidepact update <original-id> --task TASK-001 --status done --note "Actual field, type, null behavior, and checks performed"
sidepact reply <original-id> --note "Frontend follow-up and unresolved questions"
```

Read the [complete generated reply](../examples/avatar/回覆.md). It preserves `TASK-001`, has a new document ID, and references the original with `reply_to`.

**Frontend receives the reply:**

```bash
sidepact import /path/to/received/回覆.md
sidepact show <original-id>
```

The frontend agent compares the backend report with its caller and handles the agreed nullable field/default image. This closes a frontend → backend → frontend round trip. Sidepact does not modify another repo's code or send files automatically.

## 2. Only a mock is available: ask for confirmation

The same feature request arrives, but the agent only sees:

```ts
// src/profile.ts:2
export const mockProfile = { name: "Example" };
```

There is no verified API response or shared contract. Outcome: **needs confirmation**, not "backend is missing avatarUrl."

```bash
sidepact generate --note "[needs-confirmation] Does GET /api/me already expose an avatar field? Only a frontend mock is available; confirm the field name, type, and no-avatar behavior before proposing a new field"
```

Read the [generated confirmation handoff](../examples/confirmation/改動.md). `[needs-confirmation]` is an agent-supplied text label; initial task status remains `pending`.

The backend may discover an existing `profileImage` field, or confirm that a new field is needed. If discussion is still required, its agent can explicitly record:

```bash
sidepact update <original-id> --task TASK-001 --status needs-clarification --note "Verified contract and the question requiring a decision"
sidepact reply <original-id> --note "Findings and proposed next steps"
```

## 3. Layout-only change: no handoff

**User asks:**

> Center the member-page button and adjust mobile spacing.

The agent checks that only presentation changed and no external API, field, event, or capability is needed. It should report:

> No cross-repo work. This change only adjusts layout and uses the existing interface; no handoff was generated.

It should **not** run `sidepact generate` for this task or delete earlier handoffs. This is agent judgment, not built-in CSS analysis.

## Practical details

- Replace `<original-id>` with the actual handoff ID, without angle brackets. The agent can read it from output or `sidepact list`.
- For committed changes, choose the actual task start with `--base`; a clean working tree has no default diff.
- New files need staging under your project's rules. Sidepact does not stage or commit them.
- Generated files are new snapshots. Preserve `.sidepact/` (or legacy `.git-handoff/`) history for matching replies.
- Installation alone does not tell the agent to generate. Check `sidepact agent-status`, then reload instructions or start a new session.
